## Context

ServiceControl stores its data in RavenDB. Each static index uses a search engine, Corax or Lucene. RavenDB resolves the engine of an index from the index configuration, the database settings, and the server default, in that order, and stores the result with the index. A database default therefore does not change an existing index. It applies only when an index is created, reset, or replaced.

At every start-up, ServiceControl deploys its index definitions. When a definition differs from the one on the server, RavenDB builds a side-by-side replacement and swaps it in once it is no longer stale. On a large audit database this takes days, competes with ingestion, and needs storage for both indexes. A locked index does not receive the new definition.

The engine history is:

- 6.0.0 ([#4484](https://github.com/Particular/ServiceControl/pull/4484)) wrote Corax into the database settings of every database that had none, at every start-up.
- 6.20.0 ([#5833](https://github.com/Particular/ServiceControl/pull/5833)) creates new databases with Lucene, because load tests showed smaller indexes, less RAM, and better speed for ServiceControl's definitions. Existing databases kept the Corax pin, and migrating an index became an operator decision because it triggers a rebuild. The release also changed the audit `MessagesViewIndex` and `MessagesViewIndexWithFullTextSearch` definitions without an upgrade-guide entry.
- 6.21.1 ([#5946](https://github.com/Particular/ServiceControl/pull/5946)) keeps an engine that is set on an index on the server.

Three problems remained in 6.21.2:

1. The Corax pin cannot tell "never pinned" from "the operator removed the setting". RavenDB Studio removes a database setting whose value equals the server default, so the documented "Migrating the whole database" procedure on a Lucene server deleted the keys and ServiceControl restored Corax at the next start.
2. An index without an engine of its own follows the database default when RavenDB rebuilds it. In a pinned database, a Lucene index without its own setting moved back to Corax.
3. Neither developers nor operators get a signal before a definition change starts a rebuild. 6.20.0 showed that an upgrade-guide entry depends on someone noticing the change.

Adding an engine to the configuration of an unchanged index is itself a definition change, and RavenDB rebuilds the index even when the engine is the same. Any rule that sets an engine must do so only where a rebuild happens anyway. An operator's engine choice, on an index or on the database, must survive start-up. A rebuild cannot be made cheap, only predictable.

## Decision

ServiceControl no longer writes search engine settings to an existing database ([#6034](https://github.com/Particular/ServiceControl/pull/6034)). New databases are still created with Lucene. Settings written by 6.0.0 to 6.21.2 are not removed, because removing them is also an operator decision.

`IndexDeployment` resolves the engine of each index before deployment with these rules ([#6035](https://github.com/Particular/ServiceControl/pull/6035)), applied in order:

1. An engine set in the definition in code wins. A definition that sets an engine other than Lucene is logged as a warning; none of ServiceControl's definitions sets one.
2. Lucene set on the index on the server, or on its pending replacement, is kept. The pending replacement is checked first, because it holds the operator's latest choice. Another engine set on the index is kept only while the definition is unchanged, and is logged as a warning, because dropping the setting would itself rebuild the index.
3. A new index, or an index that RavenDB rebuilds because its definition changed, uses Lucene. When the database setting is Lucene, the index inherits it and gets no setting of its own. Otherwise Lucene is set on the index. This also replaces Corax set on the index.
4. An unchanged index without an engine of its own is left alone.

Rule 3 is the point of leverage. A Corax index moves to Lucene at its next rebuild, which the definition change triggers anyway, so the migration costs no extra rebuild. A Lucene index never falls back to Corax. Lucene is the only engine ServiceControl supports: it never creates a Corax index.

A rebuild is made visible instead of avoided. An approval test renders every index definition the persisters deploy, so a definition change fails review until the upgrade guide records it ([#6013](https://github.com/Particular/ServiceControl/pull/6013)). At start-up, `IndexDeployment` reports each database's engine setting, each index's engine and where it comes from, each rebuild with the differences that cause it, and each locked index ([#6036](https://github.com/Particular/ServiceControl/pull/6036)). A locked index whose definition changed, in either lock mode, stops the start-up with an error that names the index, instead of keeping the old definition silently (`LockedIgnore`) or failing with a RavenDB exception that does not name it (`LockedError`). Operators get general guidance for upgrades that rebuild indexes and for unlocking changed indexes before upgrading ([docs#8577](https://github.com/Particular/docs.particular.net/pull/8577), [docs#8645](https://github.com/Particular/docs.particular.net/pull/8645)).

ServiceControl queries only through static indexes. A dynamic query makes RavenDB create an auto index, which follows the database setting `Indexing.Auto.SearchEngineType` and has no search engine setting of its own, so none of the rules above, nor the per-index migration in the documentation, can move it to Lucene. The search engine custom check and the start-up warning keep reporting such an index after every static index uses Lucene. The retry batches ([#5953](https://github.com/Particular/ServiceControl/pull/5953)), the throughput endpoints ([#6099](https://github.com/Particular/ServiceControl/pull/6099)), and the event log ([#6100](https://github.com/Particular/ServiceControl/pull/6100)) were the dynamic queries left, and now use static indexes. The test servers run with `Indexing.DisableQueryOptimizerGeneratedIndexes`, so a new dynamic query throws in the tests that exercise it ([#6120](https://github.com/Particular/ServiceControl/pull/6120)). A query without a filter or sort, or only on the document id, is a collection query and creates no index. Production instances do not set this option.

## Consequences

- Existing databases keep whatever engine settings they have, including a Corax pin from 6.0.0 to 6.21.2. Accepted, because the database default no longer decides the engine of a rebuilt index. The setting still applies to a reset made in Studio, and to auto indexes, which ServiceControl's own queries no longer create.
- Auto indexes created by earlier versions are not deleted at start-up. RavenDB marks an auto index idle after 30 minutes without queries and deletes it after 72 hours, and an operator can delete it in RavenDB Studio. Until then, the search engine check keeps reporting it if it uses Corax. Accepted, because they cover small collections (retry batches, the event log, and throughput endpoints) and go away without operator action.
- A dynamic query in a component whose exceptions are caught and logged throws in the tests without failing them, unless the test depends on the result. Mitigation: the error persistence tests also fail at teardown when a test leaves an auto index in the error database (#6100). In production the query still works and creates the auto index, which the search engine check reports.
- An index migrates from Corax to Lucene without operator action at its next definition change. The upgrade guide entry for the first release that changes a definition on a pinned database must say so. The search engine documentation describes the behavior from 6.22.2, and warns that the "Migrating the whole database" procedure does not work on 6.20.0 to 6.22.1 when the server default is Lucene ([docs#8639](https://github.com/Particular/docs.particular.net/pull/8639)).
- An index with Corax set on the index itself moves to Lucene at its next definition change (rule 3). Accepted, because Lucene is the only supported engine and the rebuild happens anyway. Until then the index keeps Corax and start-up logs a warning. An operator who needs Corax for an index has to lock it, and then receives no definition changes for it.
- A pending replacement started by 6.20.0 to 6.21.2 for an index without an engine of its own, in a database whose setting is not Lucene, has no engine of its own either. After the upgrade, rule 3 sets Lucene on the index, so the deployed definition no longer matches that replacement, and RavenDB is expected to build a new one, losing the progress made so far. #6035 does not discuss this case, and no test covers it. Mitigation: let a running rebuild finish before upgrading. The upgrade guide does not say so yet. Keeping the replacement on Corax would leave that index on Corax until its next definition change.
- A locked index whose definition changed stops the start-up, in either lock mode. Accepted, because a `LockedIgnore` index would otherwise run with a definition the new version's queries may not match, and the error names the index to unlock. Mitigation: the upgrade guide tells operators to unlock changed indexes before upgrading ([docs#8645](https://github.com/Particular/docs.particular.net/pull/8645)). In 6.22.2 maintenance mode ran the same setup and failed too, which left a Windows deployment with an embedded database no way to reach RavenDB Studio without support. From 6.22.3 maintenance mode skips the database setup ([#6107](https://github.com/Particular/ServiceControl/pull/6107)), so the operator can unlock the index there.
- A false positive in change detection on a database whose setting is not Lucene adds Lucene to an unchanged index and starts the rebuild that rule 4 exists to prevent. Mitigated by comparing with the deployed conventions and by tests that assert an unchanged index is not rebuilt.
- The approval test adds a re-approval and an upgrade-guide entry to every index change. Accepted. Re-approving is a file copy, so the test is a reminder, not a gate.
- ServiceControl itself tells an operator about a rebuild only in the logs, once it has started. Accepted: [#6015](https://github.com/Particular/ServiceControl/issues/6015) proposed earlier warnings, with the number of documents a rebuild covers, an opt-in setting that refuses an unplanned rebuild, and a pre-upgrade check in ServiceControl Management. These are not pursued, and #6015 is closed with the start-up reporting of #6036. Mitigation: the approval test makes every definition change come with an upgrade guide entry, and the upgrade guidance tells operators to check the upgrade guides for index changes before upgrading ([docs#8645](https://github.com/Particular/docs.particular.net/pull/8645)).

## Alternative approaches

- Keep pinning existing databases, but only once, with a marker that records that the pin was applied. This would preserve the intent of 6.0.0 without overriding a later removal. It is rejected because the pin has no benefit: RavenDB stores the engine with each index, so the database default does not protect existing indexes from anything.
- Set Lucene on every index at start-up. This migrates every installation in one step. It is rejected because adding the setting changes every definition and rebuilds every index on every existing database at once, which is exactly the multi-day rebuild 6.20.0 left to the operator.
- Set the database default to Lucene during the upgrade. This makes rebuilt and new indexes inherit Lucene without a per-index setting. It is rejected because it overrides an operator's database setting, the same flaw as the Corax pin in the other direction.
- Keep following the database default for rebuilt indexes, as 6.21.1 did. This changes nothing that an operator configured. It is rejected because a definition change in a pinned database silently moves a Lucene index back to Corax, and because it wastes the one rebuild in which switching engine is free.
- Refuse to start when Corax is set on an index. This would enforce Lucene as the only supported engine. It is rejected because it stops a production service for a rare case, removes the escape hatch for support, and relies on telling an engine set on the index from an inherited one, which is not verified against a 6.x database. The warning in rule 2 gives the same message without the outage.
- Only check after each test that no auto index was created ([#6115](https://github.com/Particular/ServiceControl/pull/6115)), instead of making a dynamic query throw. It also catches a query whose exception a background component swallows. It is not adopted as the only guard because it fails at teardown without pointing to the query; making the query throw gives a stack trace. The error persistence tests keep a teardown check from #6100 next to it.
- Ask RavenDB whether an index will change with `IndexHasChangedOperation`, as [#6015](https://github.com/Particular/ServiceControl/issues/6015) proposed, instead of a client-side `Compare`. It uses the server's own rule. It is rejected: it needs one round trip per index, and it compares the definition after the engine is resolved, so it cannot inform the rule that resolves it.
- Rely on upgrade-guide entries alone to warn about rebuilds. It costs nothing in code. It is rejected because 6.20.0 shows an entry depends on someone noticing the change. The approval test makes the change visible in review.
- Gate index changes in CI or at release time: a pull request label with a required acknowledgement, or a release check that compares approved files with the previous tag. A release check would have caught 6.20.0, because it sees changes spread across several pull requests. These remain candidates for a follow-up; they were proposed in the [#6013](https://github.com/Particular/ServiceControl/pull/6013) review and not implemented.
